# 库房手工入库验收记录

日期：2026-09-07。用户确认库房暂不对接公司主系统，允许自己入库。本次为新增本地功能，不表示已部署线上。

## 实现与边界

- 正式库房班组长可从库房页面手工入库，提交直接增加库房台账。管理员、其他班组不得代操作。
- 必填流水号、材质、物料类型、件数、重量、入库说明；其余现有单据字段可选。件数重量至少一项大于 0，重量最多三位小数。
- 新批次 `entry_kind=warehouse_receipt`，来源班组为空，接收位置为库房；不是虚拟外部系统单据或库房转给自己。
- 原单提交后锁定，记录入库人、时间和 stocked 审计，生成 TL / Code 128。批次可继续出库、丢失登记及流水追踪。
- 后续出库是普通 transfer，并关联入库来源；内部转回库房仍须正常接收，不重复计为手工入库。
- 新增 GET/POST `/api/team-materials/{team_id}/receipts`、入库原单分页及索引；重复请求幂等，改内容复用同一键返回冲突。
- 不做 ERP 对接、批量期初导入、入库冲销/库存调整或外部发货业务。旧库存不自动回填。

### 真实 MySQL 8.4 验证

本机 Docker 启动完成后，在独立 MySQL 8.4.11、REPEATABLE READ 的空库 `heatsink_stock_qa` 上实际运行扩展后的 `scripts/verify_mysql_material_stock.py --confirm-disposable`，退出码 0。容器只监听随机本地回环端口，数据目录为临时 tmpfs，没有使用生产凭据、已有数据卷或服务器。

- 旧记录升级至 0008 后内容保留，重复迁移、索引和外键、整笔出库回滚、分组查询通过。
- 出库对出库、丢失对出库、丢失对丢失竞争：一笔成功、一笔余额冲突，不超扣。
- 同键重复出库、重复丢失、重复手工入库：两次请求返回同一结果，只写一笔。
- 同一个入库幂等键携带不同内容：一笔成功、一笔 409，不重复增加库存。

首轮实测发现 MySQL DATETIME(0) 将微秒四舍五入到秒，导致首次入库响应与重试响应的时间不同，但入账未重复。修正为 flush 后读取数据库实际保存的三个时间，再生成审计和响应；新增数据库时间精度回归后，在重新创建的空隔离 MySQL 库中完整重跑并通过上述七种并发场景。结果见 [MySQL 验证结果](../output/playwright/warehouse-receipts/mysql-verification.json)。

验收结束后，本次临时 MySQL 容器及 tmpfs 测试数据库已清理，可用同一脚本重新生成验证数据。本地 SQLite 试用数据及其升级前备份保留，线上数据未触碰。
