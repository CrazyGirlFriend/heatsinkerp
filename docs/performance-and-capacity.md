# 性能与容量验收

功能正确不等于容量达标。在线人数、活跃用户数、并发请求数、接口 RPS/QPS 和数据库 QPS 分开统计；不拿连接数、空库结果或单接口速度承诺整套系统容量。

本文按时间保留验证记录。当前 `20260923T110054Z` 异步/MQ 版本取消了前文的两秒结果缓存，并替换进程内提交通知；前文旧版实现描述仅用于历史对照。最新五分钟结果见文末，实际发布状态见 [部署记录](server-deployment.md)。

## 建议的首期指标要求

以下是本项目的建议验收目标，不是通用行业标准，也不是已经证明的最大容量。P95 为 95% 请求不超过的耗时，P99 为 99% 请求不超过的耗时；必须同时报告样本数、错误率及测试窗口，不能只报平均值。

| 项目 | 首期目标及统计口径 |
| --- | --- |
| 并发场景 | 25 个独立账号同时使用，保持 25 路实时连接，其中两路持续执行入库、转出、接收、丢失；查询包含不同班组和分页，不用单账号、单接口替代 |
| 普通查询 | P95 ≤ 1 秒，P99 ≤ 2 秒；不包含长连接生命周期、导出或大范围历史分析 |
| 业务写入 | P95 ≤ 2 秒，P99 ≤ 3 秒；按入库、转出、接收、丢失分别统计，成功返回必须已经提交事务 |
| 实时可见 | 提交请求开始至 SSE 收到对应批次状态：P95 ≤ 3 秒，P99 ≤ 5 秒；含请求处理，不含浏览器绘制和用户网络 |
| 错误 | 非预期错误率 < 0.1%；专项库存测试必须全部通过，不允许超扣、重复入账、失败后残留部分单据或件数重量不一致；预期的竞争拒绝 409 单列 |
| 消息恢复 | 队列不可用期间业务可正常提交、通知持久保存；恢复连接后补发并收敛到最新状态，允许重复通知但不允许重复写库存 |
| 资源与稳定性 | 不发生 OOM、异常重启或连接泄漏；测试内存触及容器上限 85%、共享主机可用内存不足 2 GiB 或近期查询 P95 > 3 秒即停止加压 |

每次发布至少完成 5 分钟有数据的混合验证；正式定容量还需预期业务数据规模、30 分钟以上稳定期和更长耐久测试。当前探针使用几百条物料记录，不能替代大历史库验收。写入仅几十个样本时 P99 接近最大值，只作短测观察，不作尾延迟保证。

在线人数不等于每秒请求数。RPS 报告实际完成的 HTTP 请求/秒，业务 TPS 报告成功事务/秒；本探针每批动作后有等待并随通知刷新，结果不是最大 QPS。50/100 人或持续突发负载必须另做逐级测试，通过前不承诺支持；首次增加 worker 也要重新计算总连接池、验证权限及消息广播。

## 每轮要核对的指标

| 维度 | 验收内容 |
| --- | --- |
| 场景与数据量 | 活跃用户数、请求间隔、页面比例、每次操作接口数量、流水号/批次数和历史跨度；说明是否真实浏览器、是否同一账号 |
| 吞吐 | 测试窗口内完成的请求数与 RPS；业务 TPS 按成功入库、提交或确认分别定义，不混入登录、心跳与查询 |
| 响应 | 查询/提交分别统计 P50、P95、P99、最大耗时和错误率；区分起压阶段与稳定阶段 |
| 实时推送 | 长连接数、首帧等待、事务提交至客户端收到更新的延迟、断线恢复和过期鉴权；长连接存续时长不是查询响应时间 |
| 服务资源 | CPU、内存、连接池等待、慢 SQL、锁等待、连接清理及容器重启/OOM；考虑同机其他服务占用 |
| 库存正确性 | 并发扣减不超扣、幂等不重复入账、确认不二次扣库、作废恢复、失败回滚、数量重量守恒、看板与台账一致 |

使用分级负载和明确停止阈值，不为找极限拖垮共享服务器。线上测试须获得许可，不向正式库存写压测数据；写入、冲突和大数据量测试使用隔离库。验收阈值与数据规模应一起约定，不能用单一“支持多少人”代替。

## 第一项：共享实时快照（已随 20260923T065006Z 发布）

- 同一数据修订版本、同一视图的 SSE 订阅共享已经序列化的快照；并发读取合并为一次汇总与序列化，库存总览和机器人大屏互相隔离。
- 提交事件推进修订号，缓存立即失效；回滚和纯读取不推进。构建期间发生提交时，不将旧事务快照缓存为新版本，连接继续接收下一轮通知。
- 缓存最多两份，不存用户、令牌或权限。每次读取（包括缓存命中）仍独立校验登录；权限数据库会话在等待共享计算之前释放。
- 本地日期变化及两秒最大缓存年龄控制新订阅的时间窗口；过期只在下一次读取时计算，不新增轮询。业务提交不等待这两秒。
- 查询、入库、扣减、确认等业务事务和行锁未改；筛选列表也未加入可能串条件或串权限的共享缓存。
- 结构化请求日志补充 `is_stream`、`first_body_ms`。分析接口 P95 时排除长连接的 `duration_ms`，SSE 单看首帧/连接生命周期；新增 `inventory.snapshot.built` 记录共享构建耗时，不记录库存内容或认证数据。首帧日志不是提交至浏览器的端到端推送延迟。

仍然是单进程提交事件，不能直接增加 worker 或多实例，否则不同进程无法互相通知。没有为本次优化引入额外服务、数据库迁移或新的监控面板。

## 第二项：列表关联数据读取（已随 20260923T065006Z 发布）

分页列表读取来源批次时，原来的 ORM 加载方式会继续加载来源的关联数据，部分分页退化为逐条补查。用真实入库、转出、接收、回库、丢失、加急操作构造 26 条转料记录后，转料列表一页 10 条触发 35 次 SELECT（含鉴权与总数查询）。

现在列表一次联查加急、来源批次号及历史出库单号；来源仅取 ID 和批次号，不展开它自己的来源、班组、加急与其他资料。六类列表共用该读取规则：转料记录、出库记录、可出库来源、库存分组下的来源明细、库房入库记录、历史合单记录。仅更改只读查询的加载方式；详情、打印、写入事务、行锁、字段、排序、筛选和分页规则保持原样。

同一测试场景下，转料列表降至 3 次 SELECT。专项检查每页 1 / 10 / 100 的请求参数（实际返回条数受样本量限制），六类列表分别不超过 3 / 4 / 5 / 5 / 4 / 6 次 SELECT；页数和记录关系不再触发逐条补查。与详情逐字段对照管理员、上序和下序的返回结果，保留前导零、加急、历史单号、权限动作及按需查看的审计/丢失记录；空页和未登录访问也有覆盖。

专项及相关业务回归共 110 项通过，后端质量检查与差异检查通过。这些是隔离 SQLite 中的查询次数与正确性验证，不是生产 MySQL 查询耗时、QPS 或容量承诺。没有新增索引或修改业务数据。本项独立提交 `bc0cac4`，已推送并随本轮后端发布上线。

## 第三项：班组汇总去重（已随 20260923T065006Z 发布）

班组汇总已经按材质取回完整的结存分类，原来还单独执行相同台账的总计查询。现在直接累加未做展示舍入的材质分组件数与重量，避免重复聚合；数据库仍负责材质分组，未改成 Python 字符串分组，不改变 MySQL 的排序/大小写归类规则。物料类型统计保持原查询。空材质也包含在总计中，空班组各余额为零。

库房待接收的批次数复用待接收记录数：批次号有数据库唯一、非空约束，一条记录就是一个批次，合在一次提交里的两个独立批次仍计两批，不需要再次扫描去重。

管理员会话的隔离 API 测试中，库房汇总从 8 次 SELECT 降到 6 次，普通班组从 7 次降到 6 次（均包含鉴权和班组查询）。不缓存班组汇总，也不改变库存公式；三位小数、废料、纯重量、缺失材质、未跟踪历史单、待接收、部分接收及作废恢复均与批次台账逐项核对。
