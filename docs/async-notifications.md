# 异步接口与消息队列

本次改造的范围是现有 HTTP 接口、实时通知和库存读取，不新增审批、通知中心或异步库存任务。已随后端 `20260923T110054Z` 发布，版本、备份及验收细节见 [部署记录](server-deployment.md)。

## 执行方式

- HTTP 路由与鉴权使用异步入口；MySQL 使用 SQLAlchemy `AsyncSession` 和 `asyncmy`。
- 已有事务业务函数通过 `AsyncSession.run_sync` 执行。这里是 SQLAlchemy 官方的协程桥接，SQL I/O 使用异步驱动，不是用同步 PyMySQL 阻塞事件循环。
- 密码计算、暂时只有同步实现的主系统 HTTP 适配器，通过 `await asyncio.to_thread` 隔离；不在事件循环里直接等待。迁移、初始化和维护 CLI 仍可使用同步连接。
- 入库、出库、接收、丢失和库存余额在同一数据库事务中提交，成功后才返回业务成功。**不会把扣库存扔进队列、提前返回成功。**
- 库存读取不保留两秒结果缓存。只有同一版本、同时进行中的全厂推送构建共享一次计算；任务结束即丢弃。库存余额机制见 [事务库存余额](transactional-stock-balances.md)。

## 通知怎么走

1. 业务变化和 `notification_outbox` 待发记录在同一 MySQL 事务落库。事务回滚，通知也回滚。
   本地修复将同一事务的多次 flush 合并为一条通知，包含全部受影响班组；成功的保存点并入外层，回滚保存点不产生通知。仍然在数据库提交前写入 outbox，不使用提交后的不可靠内存补写。
2. 异步发送器领取最多 10 条，设置 120 秒租约；释放数据库连接后发送到 RabbitMQ。
3. RabbitMQ 使用持久交换机、持久队列、持久消息和发布确认。发布确认成功才记录 `published_at`；失败保留记录，按 2～30 秒退避重试。
4. 每个服务进程独立订阅广播队列，手动确认消费，然后通知自己的 SSE 客户端。多进程不会相互抢走另一进程需要的通知。
5. 库存、转料、加急、班组目录、业务类型、期初提交、账号变化和会话撤销均使用这条通道。载荷只包含变化范围、账号 ID 和不可逆会话摘要，不包含密码、明文令牌、客户资料或库存快照。

这是“至少一次”投递：进程可能在发布成功、记录确认之前退出，因此允许重复通知。消费者只触发重新读取，**不执行库存写入**。多个积压通知可以合并为一次最新状态更新，不保证浏览器逐条重播历史通知。

## 中断与恢复

- RabbitMQ 不可用：业务写入和 HTTP 查询仍可继续；待发通知留在 MySQL。SSE 新连接返回 503，已有连接在发现断开后结束，前端显示重连，不伪装为实时在线。
- 发送器中断：其他进程在租约到期后接手。连接恢复后，每个进程通过 RabbitMQ 广播一次全量失效通知，在线页面重新读取当前数据。
- 浏览器重连：先读取完整当前状态，再订阅后续更新；它不是可靠历史消息的存储端，历史明细以业务表为准。
- 非法消息进入 `heatsink.notifications.dead` 死信队列，不进入无限重试循环。死信应由运维调查后处理，不自动删除。
- 已确认发布的 outbox 记录保留 7 天，每分钟最多清理 500 条。未发布记录不自动删除。闲置进程的 RabbitMQ 订阅队列 24 小时后自动回收。
- `GET /api/notifications/status` 仅管理员可调用：返回本进程连接状态、未发布数量和最老等待秒数，不返回消息内容。持续积压、长时间重连、死信出现均需告警；本次提供状态接口和安全日志，尚未接入外部告警平台。

RabbitMQ 当前为单节点，具备进程/连接重启恢复能力，不等于跨机器高可用；服务器磁盘损坏仍需备份恢复。异步化也不能消除数据库锁等待或 CPU 瓶颈，不能凭代码结构直接承诺在线人数或 QPS。

## 延迟诊断（本地修复，尚未发布）

日志按请求 ID 串联业务提交，并按消息 ID 串联 `notification.staged`、`notification.claimed`、`notification.publish_finished` 和 `notification.consumed`。`notification.transaction_committed` 只在业务提交成功后记录；`commit_ms` 为提交阶段（包括该阶段触发的 flush），不是整笔业务处理时间。回滚的 staged 记录不代表消息已发送。

HTTP 请求与大屏构建分别记录 SQL 次数、驱动等待时间；快照编码和 SSE 帧就绪时间单独记录。驱动计时包含等待期间的调度，不包括连接池领取、SQL 编译及最终数据库提交；不能把总耗时减 SQL 时间全解释成 CPU 时间。消费日志的本地 revision 用于关联随后的快照，不是跨进程业务版本号。SSE 帧就绪也不等于浏览器已绘制。

这些日志不输出 SQL 文本、参数、业务载荷、令牌或密码。数据库 outbox 时间列的精度不足以单独推算毫秒级推送耗时，应使用关联日志和客户端端到端计时。

## 隔离验证

真实 MySQL 8.4、RabbitMQ 4.3.6 和两个独立后端进程已验证跨进程广播、重复消息不重复入账、非法消息进入死信队列。停止 RabbitMQ 后业务提交成功且通知留在 outbox，重启后待发数量从 1 降至 0，两端重新收到最新状态。异步 MySQL 等待期间事件循环仍可推进，不只检查函数名是否写了 `async`。

并发写入、迁移及五分钟混合负载结果见 [性能与容量验收](performance-and-capacity.md)。隔离容器、网络与测试数据库已清理；线上已另行通过迁移、权限、推送、余额及原始业务数据保护核验。性能数字仍是隔离环境结果，不是正式库写入压测。

## 配置及发布

- 新增 RabbitMQ 4.3.6；Compose 服务名 `mq`，卷 `rabbitmq_data`，容器内 `/var/lib/rabbitmq`。项目名 `heatsinkrep` 对应 `heatsinkrep_rabbitmq_data`。
- `.env` 新增 `MQ_USER`、独立强密码 `MQ_PASSWORD`。生产后端通过内网连接 `mq:5672`；不对外发布 5672 或管理端口。不将密码提交到仓库。
- 单独启动后端时配置 `MQ_HOST`、`MQ_PORT`，或完整 `MESSAGE_QUEUE_URL`（远程受信网络可配置 `amqps://`）。SQLite 开发测试必须使用文件库，不能使用无法共享的内存库。
- 数据库迁移 `20260923_0017` 回填并校验库存余额，`20260923_0018` 添加通知表。发布前停写并备份；先在隔离环境演练，再升级正式服务。
- 后端依赖发生变化，必须重建依赖层，不能只复制 Python 源码到旧镜像。普通和 `Dockerfile.prebuilt` 构建均会安装固定版本依赖；保留单 worker 部署默认值，不自动调大连接池或 worker 数量。
- 建议顺序：配置并启动 RabbitMQ → 停业务入口及旧后端 → 备份 → 单实例迁移及账目核对 → 启动新后端 → 检查通知状态及真实收发 → 恢复入口。
- 不要在新版本已产生业务后直接启动旧版写入程序：旧版不会维护余额表。回退必须停写，明确数据库兼容和数据保留方案；不要自动回灌旧备份覆盖新增业务。

## 迁移到另一台机器时的补充

已使用本版本时，仅搬 MySQL 不等于搬完消息队列。先停业务写入、等待 outbox 发送完成，再停后端和 RabbitMQ；同时备份 MySQL（包括待发记录）及已停止的 RabbitMQ 数据卷、镜像版本和配置。恢复 RabbitMQ 要保留节点名/hostname、Erlang cookie、用户权限及数据目录，先隔离演练。不要复制运行中的 RabbitMQ 数据目录。

如果只需要恢复页面刷新通知，可以在经确认的恢复方案中重建队列，并通过全量快照恢复页面状态；这不保留历史死信。不要擅自把这种降级当作完整消息备份。旧版迁移步骤见 [服务器迁移](server-migration.md)，应使用与实际运行版本配套的 Compose。
