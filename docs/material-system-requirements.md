# 物料系统大小循环与编号历史需求

> 状态：历史方案，不作为当前一期实施依据  
> 确认日期：2026-09-05  
> 需求来源：桌面文件《物料系统需求》及现场补充说明

> 2026-09-06 一期范围已经收缩为纯班组间物料流转。当前实现以 [一期物料流转口径](phase-1-material-transfer.md) 为准：暂不接工艺、工单、报工、产量和公司主系统大循环；管理员只管理班组与班组长。本文保留供后续阶段讨论，不得据此扩展一期页面或校验。

## 1. 核心结论

系统需要分成两个相互衔接但职责不同的循环：

- **大循环**：公司主系统负责订单或工件主信息以及公司级出库、入库和库存结果。
- **小循环**：本系统负责热沉车间内部各工序之间的加工、转料、接料、异常和在制品位置追踪。
- 大循环和小循环只在明确的出入库边界交换数据，不能把公司主系统的库存逻辑复制到本系统中各自维护一套。
- 公司主系统是公司级库存结果的权威来源；本系统是车间内部在制品、转料批次和工序轨迹的权威来源。

## 2. 四类编号必须分开

| 编号 | 业务含义 | 是否作为条形码 | 主要用途 |
| --- | --- | --- | --- |
| 公司主系统单据号 | 公司级出库单、入库单或接口消息编号 | 否 | 大循环记账、同步和对账 |
| 工单号 | 本系统的一张生产任务 | 否 | 管理整张任务、工艺路线和总体进度 |
| 流水号 | 从公司主系统取得订单或工件基本信息的索引 | 否 | 查询产品、客户、材质、规格、技术要求等工件信息 |
| 转料批次号 | 某一次从上序向下序提交的具体物料信息 | 是 | 唯一定位本次转料、打印、扫码和接料 |

数据库内部自增 ID 不得直接代替上述业务编号。

### 2.1 流水号

- 输入流水号后，从公司主系统读取订单或工件基本信息。
- 流水号描述的是工件或订单主信息，不描述某一次转料动作。
- 同一流水号在不同工序、不同时间可以产生多个转料批次。
- 一个流水号对应一组工件或一张生产任务信息，不采用“每个物理零件一个流水号”的方式。
- 第一版按“一张工单对应一个流水号”设计；同一流水号下允许产生多个转料批次。

### 2.2 转料批次号

- 上序每提交一次实际转料，就由本系统自动生成一个持久化且全局唯一的转料批次号。
- 批次号格式按 `TLYYYYMMDDNNNNNN` 实现，其中日期取创建日期，末尾为六位顺序号；批次号创建后不可修改或重复使用。
- 同一工单、同一流水号、同一对上下工序都允许分多次转料，因此可以有多个转料批次号。
- 一个转料批次只关联一个流水号、一个上序和一个下序，但允许包含多个物料类型明细行。
- 条形码采用 Code 128，编码内容必须严格等于转料批次号。
- 下序扫描条形码后，应唯一定位该次转料，无需再从同一工单的多个报工记录中手工选择。
- 批次号必须作为正式业务字段保存，不能临时用数据库自增 ID 拼出后只在接口响应中显示。

### 2.3 原料批号

- 转料单中的原料或材料批号，与转料批次号不是同一个概念。
- 数据模型和页面命名中应使用“原料批号”或 `material_lot_no`，避免继续用含糊的 `batch_no` 与转料批次冲突。

## 3. 大循环

大循环由公司主系统和本系统接口共同完成：

1. 用户输入流水号。
2. 本系统从公司主系统读取订单或工件主信息。
3. 公司主系统完成原料或物料出库，并把已确认出库数据传给本系统。
4. 本系统以实际出库数量和重量作为车间小循环的起始库存，不能直接以计划数量代替实际出库。
5. 物料在本系统内完成所有工序流转。
6. 成品、余料、废品、废料、废泥、废屑等结果按类别汇总，形成待公司主系统入库数据。
7. 公司主系统确认入库后，大循环才真正闭环。

大循环至少保存：

- 外部系统名称和环境。
- 外部订单或工件标识。
- 外部出库单号、入库单号和接口消息 ID。
- 方向：公司主系统出库到车间，或车间完工后入库到公司主系统。
- 数量、重量、单位和物料类型。
- 待同步、同步中、成功、失败等同步状态。
- 请求时间、确认时间、失败原因和重试次数。
- 请求与响应的可审计摘要，敏感凭据不得写入日志。

所有接口消息必须支持幂等、失败重试和人工对账。收到重复或乱序消息时不得重复增加库存。

## 4. 小循环

小循环完全由本系统负责：

```text
公司主系统确认出库
        ↓
热沉内部库房转出至首序
        ↓
本工序加工或报工
        ↓
创建本次转料批次并打印批次条形码
        ↓
下序扫描批次条形码并确认数量和重量
        ↓
物料位置转移到下序
        ↓
继续后续工序，直至车间完工
        ↓
形成待公司主系统入库结果
```

- 产品走哪些工序、上序和下序是谁，仍由产品工艺路线决定，不能写死为固定班组顺序。
- 库房是每条工艺路线的固定起点和终点：第一张批次为“库房 → 首序”，最后一张批次为“末序 → 库房”。
- 库房边界是收发位置，不是需要人工报工的加工工序。
- 文档列出的库房、轧制、退火、线切割、雕刻、研磨、质检和电镀是现有业务地点或工序样例，管理员仍可维护班组和产品工艺路线。
- 每次上下序交接都是一次明确的“上序转出、下序接收”。
- 每个转料批次只绑定并显示本次的两个相邻节点，不复制或绑定整条多工序路线。
- 一个报工结果可以拆成多个实际转料批次；报工记录和转料批次不能继续隐式视为同一条数据。
- 报工和转料在数据库中使用不同业务记录；前端允许通过一次“报工并转料”操作连续完成两步。
- 同一转料批次允许按既有规则分次接收时，必须显示已接收、待接收和批次状态。
- 上序提交转料后，相应数量和重量从上序可用量扣除并进入“在途”；下序扫码确认后再进入下序已接收。
- 下序允许少收和分次接收，但不允许累计超过批次转料数量或重量；未接收差额继续留在在途，结束差额时必须登记丢料、退回或其他原因。

## 5. 转料批次内容

每个转料批次至少保存：

- 转料批次号。
- 关联工单号和流水号。
- 产品、客户、材质、规格和技术要求快照。
- 物料类型。
- 原料批号或来源批号。
- 本工序、下工序、转料班组和接料班组。
- 转料数量、数量单位和转料重量。
- 转料人、转料时间、接料人和接料时间，时间精确到分钟。
- 已接收数量、已接收重量、待接收数量和待接收重量。
- 备注、异常原因和来源记录。
- 创建、待接收、部分接收、已接收、异常和作废等状态。

物料类型至少包括：

- 成品
- 成品余料
- 半成品余料
- 废品
- 废料
- 废泥
- 废屑

数量和重量是两个独立维度。部分物料可能只有重量或只有件数，具体必填规则应由物料类型配置，不能假设所有物料都只有件数。

## 6. 扫码与接料

- 扫码枪继续按 HID 键盘使用，输入批次号后发送回车。
- 前端不调用摄像头、蓝牙或厂商 SDK。
- 扫码查询对象从工单改为转料批次。
- 扫描后直接显示该批次的流水号、工件信息、来源、去向、数量、重量、物料类型、已收和待收情况。
- 下序人工核对实物后确认接收数量和重量。
- 系统校验当前账号绑定班组是否为目标班组，管理员代操作时也保留真实操作者和代操作班组。
- 每次接收使用幂等键，避免扫码枪重复回车或网络重试造成重复入账。

## 7. 修改与删除规则

- 转料批次尚未被下序接收前，本工序可以在权限范围内修改或删除。
- 一旦下序发生首次接收，即使只是部分接收，该批次也立即锁定，不允许直接修改或删除上序转料信息。
- 后续纠错应使用单独的冲销、退回或审批流程，不能覆盖原历史。
- 打印后但尚未接收的修改必须保留版本或打印历史，补打不得覆盖首次打印记录。

## 8. 查询与追溯

系统应支持分别输入以下编号查询：

- 工单号：查看整张生产任务和总体工艺进度。
- 流水号：查看对应工件信息以及各工序当前物料情况。
- 转料批次号：查看本次转料、打印、扫码、接收和异常详情。
- 公司主系统单据号：查看出入库同步和对账结果。

流水号视图需要汇总：

- 各工序当前持有的物料类型、数量和重量。
- 已转出、在途、已接收、加工中和待公司入库数量。
- 全部转料批次及其上下序关系。
- 异常、丢料、转废和其他原因。
- 大循环的外部出库与入库状态。

如果未来出现拆批、合批或跨流水号共同转料，需要用批次来源关系保存谱系，不能只保留最终合计数。

## 9. 打印

- 工艺单和转料单是不同打印对象；第一版转料单默认制作 A4 上下双联版式，上联为存根联、下联为随货联，最终联数和尺寸可在现场打印验收后调整。
- 工艺单用于整张生产任务和工艺信息，可以显示工单号与流水号。
- 转料单用于一次具体转料，必须显示转料批次号及其 Code 128 条形码。
- 转料单同时显示流水号、产品信息、本工序、下工序、物料类型、转料数量、转料重量、转料人、接料人和时间。
- 打印时间记录到分钟，并记录首次打印、最近打印、打印次数、打印人和补打原因。
- 打印记录应关联转料批次，不能只关联整张工单。

## 10. 目标数据模型

在保留现有工单和工序快照的基础上，目标模型至少拆分为：

- `WorkOrder`：生产任务和总体进度。
- `ExternalItemReference` 或等价字段：流水号及公司主系统一组工件信息快照；第一版一张工单对应一个流水号。
- `ProcessReport`：本工序加工、合格、损耗、工时和投料结果。
- `TransferBatch`：一次实际转料，拥有本系统生成的正式转料批次号和条形码，只关联一个流水号、一个上序和一个下序。
- `TransferReceipt`：针对一个转料批次的一次接收记录。
- `TransferBatchLine`：批次中的物料类型、数量、重量、单位和原料批号；用于支持多类物料时扩展。
- `ExternalInventoryMovement`：公司主系统出库、入库、同步、重试和对账台账。
- `PrintRecord`：区分工艺单打印和转料批次打印，并关联正确业务对象。

当前不建立单个物理零件级流水号；若以后需要单件追溯，再增加独立的单件码与批次明细关联。

## 11. 当前实现状态与剩余边界

本次小循环改造已经实现：

- 持久化 `TransferBatch`、`TransferBatchLine`，并按工厂日期生成唯一 `TLYYYYMMDDNNNNNN`。
- Code 128 只编码转料批次号；扫码可唯一打开批次，不再要求在同一工单下手工选择报工记录。
- 报工可拆成多个实际转料批次，创建后预留上序数量并进入在途。
- 数量和重量分次接收、禁止超收、首次接收锁定、作废和幂等规则。
- 转料批次列表/详情、工单关联批次、流水号追踪、批次打印及补打记录。
- 工单、流水号、原料批号和转料批次号在模型与界面上分别表达；旧 `barcode=order_no` 只保留为历史兼容字段。
- `ExternalInventoryMovement` 已建立本地审计/幂等数据边界，但没有伪造公司主系统消息。

仍未完成的部分都依赖外部资料或后续业务决定：

- 首序可加工量目前仍来自工单计划数量，尚未切换为公司主系统实际出库确认。
- 末序完成尚未区分“车间完工待入库”和“公司主系统已确认入库”。
- 公司主系统查询、出库、入库、重试、撤销和对账没有真实传输适配器。
- 物料类型对件数、重量、单位的最终必填矩阵，以及退回、冲销和审批流程仍待确认。
- 旧历史收料保持兼容，不自动解释为新转料批次；只有明确标记的演示数据通过显式补种脚本升级。

## 12. 后续实施顺序

1. 取得公司主系统接口文档、认证方式、环境地址和脱敏样例，冻结字段映射。
2. 明确首序出库、末序入库、撤销、重试和人工对账状态机。
3. 实现真实传输适配器，把已建的 `ExternalInventoryMovement` 台账接入出库/入库消息。
4. 按物料类型配置数量、重量和单位规则，并补充退回、冲销和审批流程。
5. 在公司主系统测试环境完成重复消息、失败重试、乱序消息和数量重量对账测试。
6. 按现场打印机、纸张与联数校准转料单，完成扫码距离和连续扫描验收。

## 13. 真实联调前仍需取得的资料

- 公司主系统查询流水号的接口文档和真实脱敏样例。
- 公司主系统出库、入库接口及成功、失败、重复和撤销样例。
- 各物料类型对数量、重量和单位的必填规则。
- 是否存在合批、拆批、跨流水号共同转料和退回上序。
- 公司主系统入库确认失败时，车间物料允许进行哪些后续操作。
- 现场打印机型号、实际可打印边距和最终每页联数；在此之前按 A4 上下双联预览实现。
