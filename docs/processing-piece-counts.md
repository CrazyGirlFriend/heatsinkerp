# 累计收发与加工件数

## 确认的业务口径（2026-09-27）

- 累计接收：按已签收、纳入库存的原单件数和重量累加。回流接收也正常计入，不区分首次来料，不做来源去重。期初入账继续沿用现有统计口径。
- 累计转出：有效转出记录合计，包括转出待确认；作废不计入。待确认只是其中一部分，不再重复加一次。
- 待接收单尚未签收，不计入接收班组的累计接收。
- 例如收到30 kg、发出30 kg、又收回30 kg：累计收60 kg、发30 kg、在库30 kg。
- 原有批次来源关联继续自动保存，用于追踪，不要求手工填来源批次关系；本轮不增加“首次／回流”分类或去重累计投入接口。

## 加工后件数变化

切割、分件、合并等可能改变件数，但不应修改原签收单，也不能凭件数变化增加重量。

操作入口：本班组库存来源明细的“加工件数变更”，或出库表单里的“更新在库件数”。填写加工后**仍在本班组库内**的实际件数和加工说明，保存立即入账。已转出的部分不参与重计。取消出库表单不会撤销已保存的件数变更。

管理员可查看记录；只有绑定本班组的有效班组账号可以操作。原签收件数、已转出件数、重量均不被改写。修正错误时再新增一条变更，保留前后件数、当时重量、时间及操作人。

例：原签收10件／100 kg，加工后在库件数改为100件，转出60件／57 kg及0件／5 kg废屑，剩余40件／38 kg。累计接收仍为原单10件／100 kg，不会因加工被增加90件来料。

各工序件数属于当时的物料形态，不能直接用“接收件数−转出件数”衡量加工损耗。重量始终沿用实际收、发、丢失账；不自动换算单件重量或生成损耗。废屑、废泥可仅填写重量，按已有转料规则形成独立批次。

## 事务保护与接口

- `GET /api/team-materials/{team_id}/stock/{lot_id}/quantity-adjustments`：当前在库件数、重量、余额版本及分页变更记录。
- `POST /api/team-materials/{team_id}/quantity-adjustments`：`source_transfer_id`、加工后`quantity`、`expected_revision`、`reason`、`idempotency_key`。不接收重量修改字段。
- 锁定来源批次及余额，校验余额版本。期间有出库、签收、丢失或件数变化，旧版本提交返回409，必须重新核对。重试相同请求不会重复入账。
- 原数量约束扩展为：原接收件数＋加工件数净变更＝在库＋转出待确认＋完成转出＋丢失。重量平衡约束不变。
- 余额、变更记录、原单历史事件和通知消息同事务写入，失败全部回滚。已有消息队列及实时刷新沿用。
- 本班组收发历史及全链路的在库曲线包含件数变更事件，不把它画成新的收料或转料。

## 开发与发布

需要新增数据库迁移 `20260927_0020`，保留原库存及单据，仅新增件数变更记录表、余额净变更及版本列。需先迁移再启动新版服务；本轮未执行生产迁移、推送或部署。不得用重新建库代替迁移。

开发验证使用临时SQLite，不修改生产库存。迁移重复执行及保留旧记录、件数拆分与重量守恒、原单不可变、回流累计、重复提交、版本冲突、作废恢复、权限、提交失败回滚及通知测试均须通过。前端须验证草稿保留、重试、只读与曲线，再进行类型检查和生产构建。
