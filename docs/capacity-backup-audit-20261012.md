## 实测与修复

当前：37 张数据库表、1,894 条物料转料记录、5,088 条物料事件、1,548 条批次余额。MySQL 表及索引约 13 MB，数据卷约 325 MB；共享服务器约 16 GB 内存，MySQL 容器上限 1 GB、缓冲池 256 MB。根分区约 993 GB，已用 924 GB，剩余 69 GB（94%）。检查后段 MySQL 容器 RSS 约 977 MiB，已接近 1 GiB 上限，未发生 OOM 或重启；扩量前需重新核定内存预算，不能直接增加连接数。应用目录约 1.8 GB，发布备份约 9 MB，不能把共享服务器磁盘占用都归因于本项目；未删除其他项目数据。

在生产库只读事务中，以相同参数对比现有输入提示实现与候选实现，返回内容完全一致：

| 提示场景 | SQL 次数（前 → 后） | 单轮耗时（前 → 后） |
| --- | --- | --- |
| 20 条流水号建议 | 97 → 2 | 757 → 41 ms |
| 11 条材质建议 | 50 → 1 | 220 → 24 ms |

修复改为成批读取必要字段，避免每个建议再加载整条单据及关系。模糊匹配、完全匹配优先、前导零、自动补充字段和共投关联保持原语义。**减少查询次数不等于已经解决亿级模糊检索。**

其他改动：

- 浏览器 Excel 导出增加 10,000 条保护，超过时提示缩小日期/班组筛选。开始读取前、分页响应后和构建文件前均检查，不静默截断，也不改变物料件数/重量业务规则。超大导出仍需后续后台任务。
- Nginx 对静态 JS/CSS/SVG 开启 gzip，保留现有资源缓存，不改变 API/SSE 流式传输。隔离 Nginx 的实测中，92,767 字节 JS 压缩为 32,980 字节，解压内容完全一致；不是端到端页面渲染耗时。

当前线上只读单轮抽样：库存首屏 344 ms、综合搜索 477 ms、指定流水号 261 ms、第 10 页 252 ms、全厂总览 373 ms。113 批次的全链路追踪约 510 ms，未压缩 JSON 约 581 KB。上述测量包括服务函数与序列化，不包含用户网络和浏览器绘制；SQL 编译、缓存和共享服务器负载都会影响结果。

最近窗口内应用日志没有发现 5xx，但真实业务样本仅几十次，不能作为并发稳定性结论。无浏览器启动，无生产业务测试写入。

## 亿级数据之前必须处理的部分

| 问题 | 当前实现 / 影响 | 建议实施方式 |
| --- | --- | --- |
| 模糊检索 | 多字段 `%关键词%`、提示的分组排序会随历史增长扫描大量记录；共投匹配的 OR/EXISTS 也可能使精确流水号查询走时间索引扫描 | 优先明确流水号/批次号精确或前缀查询，按实测重写共投检索执行计划；建立独立流水号资料索引，模糊检索需要专门搜索索引或限定范围 |
| 深翻页 | 多处 `COUNT + OFFSET`，越往后跳过的记录越多 | 历史列表改游标分页，稳定排序 `(时间, id)`；总数独立统计，保持筛选和权限一致 |
| 库存与全厂统计 | 已有事务内维护的批次余额表，但分类、趋势和排行仍现场聚合；部分分类查询先按整班组聚合，再做筛选 | 沿用余额表维护汇总，日/月统计增量更新；适合的条件下推至聚合前，避免改变分类和库存口径 |
| 全链路图 | 一个流水号的单据和事件全部读取、序列化、渲染 | 按来源批次或时间窗口加载图，详情与历史按需读取；总计由独立汇总保证完整，不静默丢掉节点 |
| 大量导出 | 目前在浏览器组装 Excel | 保留本轮容量保护；大型导出转为后台异步任务，读取一致性快照、生成文件和可审计下载，不循环调用百万页列表 |
| 存储、索引与维护 | 现有内存/磁盘是小数据共享配置；仅靠扩充索引会进一步放大写入与备份成本 | 独立数据库资源、历史归档与冷热分离；评估分区的唯一键和外键约束，不直接在生产给亿级表加分区 |
| 持续备份 | 全备与持续日志同机，不具备主机级容灾 | 当前先完成恢复窗口；增加独立主机后配置副本、异地版本备份和告警，定期演练 |

例如即使每条记录只有 1 KB，1 亿条原始数据也约 100 GB，还没有算索引、事件历史、日志与多份备份。不能根据当前 1,894 条样本线性推算精确容量或延迟。

下一阶段应在隔离环境分 100 万、1,000 万、1 亿条逐级构造代表性数据，同时覆盖不同流水号分布、单流水号大量分批、共投、加工和跨年历史。分别验收 P95/P99、吞吐、锁等待、恢复时间和页面可操作时间；读写并发、导出和看板同时在线，不拿单条 SQL 替代业务验收。
