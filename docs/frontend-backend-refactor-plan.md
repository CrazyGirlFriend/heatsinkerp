项目已有 Ruff、ESLint、Prettier、TypeScript 严格检查和 CI。本次重点是补齐职责边界、复用规则、文档和完成标准。现有架构文档中“不接工艺、报工”等旧说明需要更新，不能据此删除当前业务。

## 代码规范与复用规则

| 方面 | 执行规则 |
| --- | --- |
| Python 代码规范 | 遵循 PEP 8 的命名、缩进、导入等原则；自动格式以现有 Ruff 配置为准，保留项目的 100 列约定。 |
| 前端规范 | 使用 Vue 3 和 TypeScript，由 ESLint、Prettier 自动检查；接口类型明确，避免用 `any` 绕过错误。 |
| 组件复用 | 按钮、输入框、表格、筛选、弹窗、提示和加载动画统一走现有共享组件。新增前先查已有实现，共性的样式调整在组件层完成。 |
| 前端逻辑复用 | 有状态的交互抽到 composable，纯计算放工具函数，接口请求放 services；页面负责组合，不同时承担所有职责。 |
| 后端分层 | 接口层处理请求和身份；业务层处理库存、加工、返工、交货规则及事务；查询模块处理列表和统计；Schema 处理数据结构校验。 |
| 设计模式 | 按实际需要使用工厂或策略。文件预览按类型选择处理器可用注册表或工厂；普通库存查询直接用函数。认证和数据库会话优先复用 FastAPI 的依赖注入。 |

组件不重复，业务计算也不重复。库存剩余数量、加工状态、返工轮次、滞留时间、交期完成率应有明确的后端计算来源，库存页、排期页、概览页统一使用。

拆分依据是职责，而不是单纯的文件行数。不为每个函数套工厂，不为每张表机械增加通用仓储层。对已有组件和模块，先核对调用关系，再合并确认重复的实现；保留有实际用途的适配层。

- [Vue composables](https://vuejs.org/guide/reusability/composables.html)；项目配置见 [ESLint](../frontend/eslint.config.mjs)、[Prettier](../frontend/.prettierrc.json)、[TypeScript](../frontend/tsconfig.app.json)。

## 前后端分层架构

前后端分离规定浏览器和服务端通过 API 通信，内部仍需划分职责。PEP 8 属于代码规范，分层属于架构设计，工厂、策略、适配器等属于解决具体问题的设计模式，三者分别约束不同层面。

整体采用按业务模块划分的分层架构：前端继续使用 Vue，后端保持模块化单体部署。业务模块包括库存收发、加工返工、工艺排期、统计通知及账号配置。以模块的公开接口协作，避免相互调用内部辅助函数和循环导入。现有文件逐项归位，不通过一次大规模改目录来代替职责整理。

以下是目标边界，需要在实施中核对和补齐，不表示当前代码已经全部符合。

### 前端职责

| 层次 | 职责与现有入口 | 边界 |
| --- | --- | --- |
| 页面与路由 | `pages`、Router，组合页面、读取导航参数、触发业务操作。 | 不直接拼 HTTP 请求，不重算权威库存和交期状态。 |
| 业务组件与交互 | 库存、加工、排期等业务组件及 composables，管理表单、筛选、异步加载和交互流程。 | 复用基础组件和服务；切换班组、账号或关闭页面后丢弃过期响应，释放订阅和资源。 |
| 共享 UI | `App*`、`Workspace*` 作为稳定入口，Watermelon 与 Element Plus 作为适配实现。 | 负责主题、动效、可访问性和通用交互，不请求库存或排期接口，不持有业务数据副本。 |
| API 与契约 | `services`、`types`、统一 `httpClient`，负责请求、响应类型、认证和错误转换。 | 不依赖页面和 UI 组件；逐项核对并解除现有反向依赖。 |
| 状态与纯工具 | Pinia 保存跨页面共享状态，局部草稿保留在组件或 composable；工具函数处理纯格式化与计算。 | 不把全部表单塞入全局 store；不重复保存可派生状态，工具函数不反向引用业务页面。 |

典型调用为：页面发起操作，业务组件或 composable 调用 API service，service 复用 `httpClient`。共享 UI 由页面和业务组件组合使用，不需要让每次请求穿过所有层。

### 后端职责

| 层次 | 职责 | 边界 |
| --- | --- | --- |
| API 层 | Router、Pydantic Schema、登录身份、请求参数与响应格式、HTTP 错误映射。 | 不在路由函数里实现整套库存扣减或排期算法；前端权限提示不能替代服务端检查。 |
| 应用服务层 | 组织入库、转出、签收、加工登记、返工、排期调整等业务用例，协调权限、事务、幂等、版本检查与审计。 | 每个写入用例有清楚的事务负责人，内部协作函数不得自行提交部分结果。 |
| 业务规则层 | 数量与重量规则、工序与返工轮次、状态转换条件、交期判断等；优先使用可独立测试的函数或小型策略对象。 | 规则不依赖浏览器、FastAPI 请求对象、RabbitMQ 或文件转换工具；整理时逐步将 HTTP 错误映射移至接口边界。 |
| 数据与外部适配层 | SQLAlchemy 查询与持久化、数据库锁、RabbitMQ、文件预览及外部系统访问。 | 按明确职责提供查询函数或业务仓储；不为每张表机械生成通用 CRUD 仓储。外部实现变化通过适配器隔离。 |

应用服务调用规则和数据访问模块，外部客户端通过现有依赖注入提供。规则层不反向导入 API 层。只有需要隔离外部实现、替换实现或明确测试边界时才引入接口或 Protocol，不为所有函数增加抽象类。

库存列表、排期看板、概览统计采用专门的查询入口和响应模型，共用权威业务计算。业务写入仍使用同一数据库和现有事务机制，暂不增加独立读库、事件溯源系统或微服务拆分。

### 前后端契约

- 以 Pydantic Schema 和 OpenAPI 为接口契约来源，核对字段名称、状态枚举、件数与重量、精度、单位、时区、空值含义及分页筛选规则。
- 先补齐缺失的请求和响应定义，再评估用成熟工具生成 TypeScript 类型；已生成的同名类型不再手写维护。服务层保留业务调用入口，不让页面绑定生成器细节。
- 写入接口明确幂等键、版本冲突与校验错误；前端提供即时校验，后端负责最终业务合法性。
- 重构保持现有 API 兼容；确需变更契约时同步调用方和契约测试，不能只改一端。

架构参考：[Microsoft 分层架构说明](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures)。此处借鉴职责划分原则，技术栈仍为现有 Vue 与 FastAPI。

## 设计模式选择与落点

下表区分现有机制、明确采用的整理方向和满足条件后才引入的模式。不能把候选项当作已经实现。

| 模式或机制 | 本项目落点 | 采用方式与验证重点 |
| --- | --- | --- |
| 组合与配置驱动 | 八个班组的菜单、功能入口、表格列、操作区域。已有 `teamWorkspaces.ts` 和共享工作台。 | 复用业务组件，用能力配置和插槽表达差异；不复制八套页面。服务端仍独立校验实际权限。 |
| 适配器 Adapter | `App*`、Watermelon、图表与文件预览、外部系统接口。已有 UI 和 HTTP 适配入口。 | 向业务提供稳定接口，封装第三方库差异；验证事件、插槽、焦点恢复、错误处理和资源释放。 |
| 门面 Facade 与应用服务 Service Layer | 入库、转出、签收、加工、返工等完整操作。现有事务服务是基础。 | 页面调用清楚的业务入口；服务协调多个模块，不继续堆成承担全部业务的超大类。 |
| 策略 Strategy | 已有普通按件加工与拆分加工的规则差异，见 `processing_registration.py`。 | 共用事务流程，只分离确实不同的校验和产出计算。若简单函数和配置足够，直接复用；出现重复分支时再抽策略。 |
| 工厂或注册表 Factory / Registry | 根据已确认的加工能力选择策略，或按文件类型选择已有预览处理器。 | 工厂解决处理器的选择与创建，策略解决具体行为。简单选择用注册表；需要依赖组装时使用工厂函数，不增加无用途的多层工厂。 |
| 显式状态转换 | 待签收、已签收、已作废，以及加工、返工和排期流程。现有 workflow 模块作为入口。 | 明确允许的操作及前置条件，状态切换统一校验权限、版本和数量；简单流程用转换表或函数，不为每个状态建类。加工进度等派生状态不允许随意手工覆盖。 |
| 工作单元 Unit of Work | 一次操作涉及库存余额、流转记录、审计和通知。 | 直接复用 SQLAlchemy Session 与事务上下文，不另写事务框架；验证失败全回滚、重试不重复扣库及实际 MySQL 行锁语义。 |
| 发布订阅与事务消息 Outbox | 已有 `inventory_events.py`、`notification_queue.py`，以及前端 `inventoryChanges.ts`。 | 复用业务和 outbox 同事务落库、提交后发布、失败重试及共享 SSE 订阅；通知用于刷新权威状态，不用重复消息再次执行库存写入。 |
| 查询与写入职责分离 | 库存、排期、统计的复杂查询，以及入库、加工、转出等写入。已有查询模块拆分。 | 借鉴 CQRS 的职责分离，共用数据库和业务定义；按需要区分读写响应模型，不引入第二套库存真值。仅搬移查询函数不等于完成 CQRS 架构。 |

事务与模式参考：[SQLAlchemy Session](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)、[事务 Outbox](https://microservices.io/patterns/data/transactional-outbox.html)、[CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)。

具体以“加工登记后转出”为例：页面复用现有转出表单；加工登记服务按服务端确认的能力选择普通或拆分加工规则；转出服务在本次转出事务中校验权限、库存、工序和批次，写入转料、余额变化、审计及 outbox；提交成功后发布通知，库存与排期页面重新读取结果。加工登记和转出是各自明确的业务操作，不能为了套用模式擅自合成一个长事务。

每个拟引入的模式需在复用清单中记录：当前重复或耦合问题、现有实现、选用方式、调用方迁移、行为验证和旧实现删除条件。统一遵循单一职责、组合优先、避免重复、保持简单；只有存在真实变化点时才抽象。

- 既有应用服务中的 HTTPException 保留为错误兼容适配；加工纯规则独立于 HTTP 与 ORM。上传、HTTP 下载响应和参数转换留在 Router，不为形式统一新增异常或仓储框架。
- 前端表单草稿、格式化视图及历史兼容字段可以不同于网络响应；网络契约统一由 OpenAPI 生成，业务 API 保留归一化入口。
- 转料／出库详情互相打开，以及模型末尾注册余额与消息事件的既有依赖继续保留。它们有明确用途，不通过移除功能来达到零循环数字。
