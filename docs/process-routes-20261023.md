# 派工工艺路线（本地实现，未提交部署）

## 使用流程

1. 库房在“新建入库”创建流水号时导入 `.docx` 工艺单，直接填写现有入库表单。上传后保留原件与解析快照；不会先让管理员重复录一套资料。
2. 明确识别的流水号、材质、客户、来料件数、规格与交期等自动带入。文件带入的输入框和标签用淡绿标记；当前值与原文不同则显示“已修改”。手填内容不被导入覆盖；换文件仅替换未修改的自动值，原件内容不变。
3. 导入后默认保持完整表单；工作人员点击“查看原始 Word”才展开左侧表单、右侧原文件。原文件预览直接展示上传的 Word，读取其原有表格、合并单元格、字体样式、页眉页脚和备注；支持适合宽度、50%–150% 缩放、放大和下载。字段差异另放“字段对照”，不把解析摘要冒充原件。文件只在系统内读取，不上传到外部转换服务。
4. 来料件数、订单数量、计划加工数量分别核对。没有明确单位的重量不猜为 kg；单位或含义不明确的内容留待手工确认。共投名单自动生成，主流水号的客户、规格和交期不会复制给其他流水号；计划重量、件数和切割尺寸仍须分别确认。
5. 入库人核对执行班组、业务与具体任务。“中转库”直接对应现有库房，重复研磨或退火按不同工序保留。工艺核对弹框沿用本次入库流水号名单，确认只返回表单，不提前发布。库房通过工艺专用只读接口查询各班组任务，不能管理其他班组任务。
6. 点击确认入库后，在同一事务核对版本、发布工艺、创建库存并关联起始库房工序。任何一步失败都不留下半份库存；响应不确定时沿用原请求重试。明确的工艺版本冲突解除只读，刷新后重新核对。
7. 班组加工带出当前业务、任务和完整工艺要求，登记加工人、实际日期、产出与未加工余料。分批加工、分批转出各自维护工序。正常产品由后端禁止跳序、换班组及未加工转出，手工单或修改待签收单也不能绕过。
8. 已发布工艺可按流水号建立小时级交货排期。节点沿用同一工艺，分批有效转出自动累计；库房不考核交货完成量。管理员工艺页面用于查询、维护和修订，已绑定批次不自动覆盖新版本。

## 共投与返工

共投工艺明确公共工序、实际拆分点和各流水号分支。拆分前实物仍只计一份；未到拆分点不能分给具体流水号。实际拆分保留原有计划重量、切割尺寸、件数和分配关系，产出批次各走对应分支；未加工余料保留之前已完成的工序，不重新计算已完成的公共加工。

废料沿用原有废料处理流程。返工沿用人工决策及原加工记录，原工艺游标不自动向前推进；跨班组返工完成须返回原工艺班组。计划再次经过某班组属于正常工序，不伪装成返工。加工记录、质量反馈、库存详情和链路批次详情均可查看对应工序；质量记录保存当时工序快照。

同一批料在同一班组的不同加工方式，以路线中的具体工序区分。例如粗磨、精磨可以使用同一班组任务，但必须保留不同工序序号及各自工艺要求。加工记录保存实际执行时的要求快照，返工精确关联选定的原加工记录并沿用其工序和要求；不按班组或任务名称合并返工来源。日报保留工序维度，返工工作量与首次完成量分开。旧记录未保存的本道要求显示未记录，不用当前要求补写历史。


## 兼容与存储

- 迁移 `0047` 只新增工艺表、工序检索索引和可空关联，不猜测补写历史路线。启用时保存界限时间；此前物料及其后续在途链路沿用原流程，新入库正常产品首次转出须关联已发布工艺。
- 原始 Word 存入数据库，随现有数据库备份一起保留；每文件最多 5 MB、解压后总大小最多 20 MB，禁止实体声明，最多 100 道工序。不执行宏、外链或文档中的指令。
- 发布时建立按工艺、流水号、工序的复合主键索引，供“可加工批次”查询识别同班组计划重复工序；不在分页后用 Python 过滤。
- 草稿采用版本检查；库存绑定、加工、出库和排期关联分别在原有事务中完成。批量出库缓存同来源工艺与接收业务查询，查询数量不随明细行数增加。
