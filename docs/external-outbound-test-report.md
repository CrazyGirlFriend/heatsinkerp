## 业务结果

- 内部转料仍必须选择不同的真实接收班组，由该班组整批确认。
- 库房对外出库、检验发货均使用真实已入账来源；单批/批量提交后预留可用量，由本班组逐条 TL 确认。
- 外部去向必填，没有内部下序；确认状态为 dispatched，不产生任何内部待接收或库存。确认后锁定，记录确认人、时间及审计。
- 待确认可以改量或作废；去向不可逐条改变，改去向需作废重建。管理员及其他班组不能代操作。

## 真实 MySQL 并发

MySQL 8.4.11，REPEATABLE READ，独立临时容器与一次性数据库 `heatsink_stock_qa`。验证脚本：`scripts/verify_mysql_material_stock.py --confirm-disposable`。

| 场景 | 两个请求结果 | 核对 |
| --- | --- | --- |
| 内部出库 / 内部出库 | 409、201 | 只成功一次，不超扣 |
| 丢失 / 内部出库 | 201、409 | 共用可用量 |
| 丢失 / 丢失 | 409、201 | 不超扣 |
| 重复内部出库 | 201、201 | 同一单据与完全一致响应 |
| 重复丢失 | 201、201 | 同一记录与完全一致响应 |
| 重复手工入库 | 201、201 | 只入账一次 |
| 入库同键不同内容 | 201、409 | 拒绝不同内容 |
| 对外 / 内部出库 | 409、201 | 共用来源锁和可用量 |
| 对外出库 / 丢失 | 201、409 | 不超扣 |
| 对外 / 对外出库 | 409、201 | 不超扣 |
| 重复对外出库 | 201、201 | 同一 CK 与 TL |
| 重复对外确认 | 201、201 | 状态、时间及完整审计一致 |
| 对外确认 / 作废 | 409、201 | 只有一个终态，不同时扣减与释放 |

胜出顺序由并发调度决定，上表为该次实测顺序。脚本将成功的服务操作标记为 201；真实 HTTP 确认接口返回 200、作废接口返回 204。

初次测试发现：等待来源锁的重复确认请求可能看到更新后的状态，但从 REPEATABLE READ 的旧快照中读取审计，造成响应少一条确认事件。已将确认流程的审计读取同步改为当前读，复测通过。数据库秒级时间亦在返回与审计前刷新，避免首次响应与重试时间精度不同。

同轮还验证旧记录保持、部分 DDL 后重试、重复迁移、索引和外键、整组回滚、MySQL 分组查询和模式/完成状态筛选，以及库房手工入库后直接对外确认的闭环。

验证后已删除本轮独立临时 MySQL 容器（数据在 tmpfs，可通过脚本重建）；未触碰原有三个项目 Compose 容器。本地 SQLite 预览数据与升级前备份保留。
