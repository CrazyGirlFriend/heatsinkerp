## 1. 一期目标

一期记录班组间物料流转，并包含库房手工入库、库房对外出库和检验发货的起止记录；不管理产品工艺、工序顺序、生产工单、报工、合格数量、加工工时或班组产量。

系统以批次记录一次明确的物料变动。内部转料批次表示一次班组间交接：

```text
一个转出班组 → 一个接收班组
```

同一流水号可以产生多张转料批次，系统按时间将这些批次串成物料轨迹，但不判断下一站是否符合某条工艺路线。

“已接收批次台账”的来源包括真实确认接收的内部来料，以及库房明确提交的手工入库；两者均须纳入台账，才能作为下一次出库和丢失登记的扣减来源。它记录件数与重量的流转余额，不是生产产量或公司主系统库存。

## 2. 角色

### 管理员

- 创建、编辑和停用班组。
- 创建、编辑和停用班组长账号，并将账号绑定到一个有效班组。
- 可以查看转料记录和流水追踪，但不代替班组发起或确认转料。
- 可以在流水号台账标记或取消加急，附可选原因；标记全局关联该流水号，不修改库存、单据版本或已确认记录。日期筛选与权限细节见 [日期筛选与流水号加急](date-urgency-filters.md)。
- 一期界面不提供产品工艺、工单、报工和产量管理入口。

系统保留一个既有管理员账号；普通管理功能不再创建其他管理员账号。

### 班组长

- 当前账号绑定的班组自动作为转出班组，不允许手工冒用其他班组。
- 创建本班组的待接收转料批次。
- 在接收班组为本班组时扫描并确认接收。
- 只能在接收方尚未确认前修改或作废本班组发起的批次。

库房在一期中也是一个实际班组或物料位置。它可作为首次转出方或最终接收方，但不再作为工艺路线节点，也不强制规定中间流转顺序。

## 3. 转料单内容

转出班组长手工填写：

- 流水号、接收班组、物料类型、转料件数、转料重量（kg）。
- 原单批号、材质、成品规格、转料规格、成品件数、客户代码、技术要求、备注（可选）。
- 原单附图的补充信息：编号、件号、形状、物料说明、外委单位、用途分类、三级类别、订单分类、特殊工艺说明（可选文本，不关联工艺系统）。

2026-09-06 再次核对桌面《物料系统需求.docx》第 4 条和内嵌纸质单据后确认：不管理工艺不等于删除单据物料信息。成品件数是成品信息，本次转料件数是实际交接量，两者独立；原单批号与系统自动生成的本次转料批次号独立，条形码只编码后者。分批转料各自开单。

物料类型为成品、半成品、成品余料、半成品余料、废品、废料、废泥、废屑。半成品是 2026-09-06 按用户补充要求增加的独立类型，不与原单中的半成品余料混用。数量为非负整数，重量为非负数、最多三位小数，二者至少一个大于 0。废泥、废屑可以只按重量交接并将件数填 0，不虚填件数。

新建页面要求明确选择物料类型。转入库房时，后端在创建或修改接收班组/物料类型时也强制校验分类；备注在该场景显示为“入库说明”，可填写暂存、退料或其他入库原因，仍为可选字段，不新增重复字段。向普通班组转料保留旧客户端可空类型的兼容；历史库房单据的空类型不推断、不伪造回填，允许直接确认和只修改备注。

系统自动记录：

- 批量出库的全局唯一 CK 批次号，以及每行 `TLYYYYMMDDNNNNNN` 追溯标识；独立手工转料、入库仍使用 TL 号。
- 批量单只渲染 CK Code 128 条码；独立手工单、入库单和旧 TL 码继续支持。
- 转出班组、转出人和转出时间。
- 接收班组。
- 接收人和接收时间。
- 待接收、已接收或已作废状态。
- 创建、修改、确认和作废的真实审计记录，包含操作人、时间和字段修改前后值。
- 版本号（初始 1），每次实际修改、确认、作废后递增。

转料单不包含工单、产品工艺、上工序、下工序、报工结果、合格数量或加工工时。页面用“转出班组”和“接收班组”，不再用带有工艺含义的“上序”和“下序”。

## 4. 状态与锁定

```text
待接收 ──接收方确认──> 已接收（永久锁定）
   └────转出方作废──> 已作废
```

- 待接收：转出方可以修改手工填写的单据字段，也可以作废。关联来料的出库单不能修改来源流水号、材质或单独改变整组出库的接收班组，调整件数和重量须重新校验余量。
- 接收方扫描批次后只核对原单内容并点击“确认接收”，不重新填写或修改数量、重量。
- 一期按整批确认，不做少收或分次接收。
- 实物与单据不一致时，接收方不确认，由转出方修改原单后重新提交。
- 确认成功后，转出方不能修改、删除或作废；纠错不得覆盖原记录。
- 重复扫码、重复回车和网络重试使用幂等键，不能产生重复确认。
- 编辑和接收确认提交当前单据版本。版本已变化时返回 409，前端刷新单据，用户重新核对后再操作。接收接口不允许修改单据内容。
- 修改历史与业务更新在同一事务内保存。历史单据只从升级后的实际操作开始记录，不补造以前的修改记录。

## 5. 位置与追踪

- 批次待接收时，物料状态为“由转出班组发往接收班组，运输中”。
- 批次确认后，该批物料当前位置变为接收班组。
- 接收班组继续外转时，从已接收物料选取来料批次，填写本次件数、重量并选择一个接收班组，生成关联来源的新批次。
- 流水号追踪按创建时间展示全部批次、转出班组、接收班组、件数、重量和确认状态。
- 页面显示最近一张有效批次的状态：已确认时显示“最近确认位置”，待接收时显示“最近一笔在途”及其两端班组。
- 同一流水号可能被拆成多批并同时位于不同班组；新台账用来源批次关联说明拆分去向，但不把最近一笔记录表述成整个流水号唯一的位置。历史未关联的单据不倒推来源和剩余数量。

## 6. 一期导航

- 班组工作台：正式入口固定为库房、轧制、退火、研磨、线切割、雕刻、电镀、检验八个班组。通过稳定班组编码关联管理员维护的数据库记录，不硬编码数据库 ID；每个班组有独立地址和页面配置，共用组件。
- 转料记录：查询、查看和由班组长发起转料。
- 扫码接收：扫描批次 Code 128 后整批确认。
- 流水追踪：按流水号查看全部班组间交接和当前位置。
- 班组管理：管理员维护班组。
- 班组长管理：管理员维护并绑定班组长账号。

旧工艺、工单和报工数据、迁移及必要表定义保留；旧页面和后端业务接口已删除，不仅是从导航隐藏。历史表定义独立放在 `legacy_models.py`，本期业务不依赖旧工作流。

班组工作台包含“数据分析 / 流水号台账 / 材质归类 / 待接收 / 已接收物料 / 出库记录 / 丢失记录”七个独立页面，库房另有入库记录；规则见第 9 节。库房包含转废，检验包含去毛刺和发货，不另设这三个班组，也不强制固定的工序顺序。

管理员仍维护班组和账号，现有管理权限不改。正式工作台只匹配上述八个编码，不把旧发货、转废、演示班组或任意新增班组自动增列为第九个正式入口；缺少对应记录时明确提示配置缺失。系统不自动创建账号、不修改原账号绑定，也不自动停用旧班组。现有全局只读可见性保持不变，写操作只属于账号绑定班组；查看其他班组不会获得代操作权限。

动态路由为 `/team-workspaces/:teamId`。不存在、停用或目录加载失败时显示明确状态，不在错误标题下回退展示全局数据。班组切换需关闭旧详情、回到首页并防止迟到请求覆盖新班组数据；账号重新绑定后以刷新后的当前账号为准。

从工作台打开流水追踪时保留班组与收发方向范围，并明确标注这是范围内的流转状态；全局流水追踪入口仍查看完整链路。后台刷新同一有效目录不得关闭正在填写的表单或丢弃草稿，只有实际切换、失效或账号归属变化才调整当前工作台状态。

2026-09-06 线上旧配置只读核对：共 15 个启用班组，包括旧十班组和五个演示班组，不等同于最新确认的正式八班组。实际班组尚未绑定班组长，现有五个班组账号均绑定演示班组。本轮不删除这些记录、不调整真实账号，也尚未部署新工作台。

## 7. 转料单字段接口契约

接口保持 `/api/material-transfers`，新增字段用于创建、更新、列表和详情响应。除另有注明外，新字段为可空文本；PATCH 未提供的字段保持不变，显式 null 清空可选字段。

| API 字段 | 单据名称 | 限制 |
|---|---|---|
| material_type | 物料类型 | finished / semi_finished / finished_surplus / semi_finished_surplus / defective / waste / sludge / scrap_chips |
| source_batch_no | 原单批号 | 80 字符；与 batch_no 独立 |
| material_name | 材质 | 160 字符 |
| finished_specification | 成品规格 | 240 字符 |
| transfer_specification | 转料规格 | 240 字符 |
| finished_quantity | 成品件数 | 可空非负整数，最大 2147483647 |
| customer_code | 客户代码 | 80 字符 |
| technical_requirements | 技术要求 | 4000 字符 |
| product_code / part_no | 编号 / 件号 | 各 80 字符 |
| material_shape | 形状 | 80 字符 |
| material_description | 物料说明 | 2000 字符 |
| outsourced_unit | 外委单位 | 160 字符 |
| purpose_category / category_level3 / order_category | 用途分类 / 三级类别 / 订单分类 | 各 80 字符 |
| special_process | 特殊工艺说明 | 2000 字符，仅文本 |

响应增加 `version` 正整数和 `history` 数组。每条历史包含 `id`、`action`（created/updated/received/voided）、`actor`、`occurred_at`、`changes`（字段名到 `{before, after}` 的映射）。列表返回空 history，详情返回真实历史。日期为带时区 ISO 时间，界面和打印展示到分钟。

`source_team` 和 `next_team` 增加可空 `kind`（production/scrap/warehouse），表示关联班组的当前目录分类，供库房展示判断；这不是历史分类快照。原有名称和编码继续使用开单/修改接收方时保存的快照。`notes` 在转入库房场景展示为入库说明，沿用原有 2000 字符限制、审计和锁定规则。

PATCH 和确认接收 POST 的可选 `expected_version` 用于乐观版本校验；新版界面始终传入详情版本。为兼容旧客户端，省略时不校验版本，但权限、行锁及接收后永久锁定仍强制执行。确认重试相同幂等键优先返回原确认结果，不能增加第二条历史。

数据库升级为 `20260906_0005`：增加可空字段、版本号及 `material_transfer_events` 表，不删除旧业务数据。上线前备份并执行 Alembic 升级，不能只替换前端。

## 8. 查询方式与索引

`GET /api/material-transfers` 新增以下可选参数，列表和状态计数必须使用相同参数：

- `search_mode`：`contains` 包含匹配（默认）、`exact` 精确匹配、`prefix` 前缀匹配。
- `search_field`：`all`（默认）、`batch_no`、`serial_no`、`source_batch_no`、`product_code`、`customer_code`、`material_name`。
- `material_type`：按上述八种类型精确筛选，省略表示全部类型。
- `team_id`：班组工作台范围，正整数，班组不存在时返回 404。
- `direction`：`all`（默认，转出或接收任一方为该班组）、`outgoing`（转出方）、`incoming`（接收方）。未提供 team_id 时只允许 all，其余返回 422。

工作台范围与原有单侧班组、状态、物料类型、搜索条件取交集，不覆盖原有筛选；列表总数和记录使用完全一致的条件。不传工作台范围时保留原全局列表行为，参数不改变既有读权限。方向查询沿用转出/接收班组索引，全部流转的 OR 范围由数据库选择执行计划，不承诺一定消除排序或任意包含查询的扫描。

旧 URL 和旧客户端默认保持包含搜索。全部字段 + 包含匹配仍搜索编号、材质、双方班组名称/编码和转出人。全部字段 + 精确/前缀匹配只搜索列出的六个编号/材质字段；可选具体字段进一步缩小范围。输入中的 `%`、`_` 和转义符 `!` 按普通字符查询，不当作 SQL 通配符。

批次号扫码始终走唯一批次号精确查询。流水追踪继续用独立的 `serial_no` 精确参数，按创建时间、ID 升序；普通列表按创建时间、ID 降序。原有班组、状态和分页参数不变。

数据库迁移 `20260906_0006` 新增 11 项索引：全局时间排序、状态 + 时间、转出班组 + 时间、接收班组 + 时间、转出班组 + 状态 + 时间、接收班组 + 状态 + 时间，以及原单批号、客户代码、编号、材质、物料类型各自 + 时间。各项末尾包含 ID，支持同一时间下的稳定排序。现有批次号唯一索引、流水号 + 时间和外键相关索引保留。

包含匹配不承诺可以使用普通 B-tree 范围定位；精确和前缀模式才是编号/材质的索引查询入口。前缀覆盖多个值时可能仍需要对候选结果排序，深页 OFFSET 也仍有逐步扫描成本。本轮不把这两种情况宣传为已完全消除。

MySQL 新索引在一次 `ALTER TABLE` 中使用 `ALGORITHM=INPLACE, LOCK=NONE` 创建，不支持时直接失败，不自动退回锁表复制。迁移支持重复执行；上线仍需备份、考虑元数据锁与建索引资源消耗，并在发布窗口执行。

## 9. 已接收物料、批量出库与丢失台账（本次确认）

### 页面与统计

| 页面 | 内容 |
|---|---|
| 数据分析 | 收发趋势、流水号库存排行、物料类型构成、库存停留、待交接时长、丢失情况六张图，往来分析为附加视图；不与台账表格同页 |
| 流水号台账 | 一行一个流水号，展示基本信息、结存/可用及待交接余额，进入详情查看多次转入、转出和来源余量；先汇总再分页 |
| 材质归类 | 按材质汇总已接收、确认转出、转出待确认、内部在途、丢失、当前库存及可用件数和重量，另有材质分布图 |
| 待接收 | 本班作为接收方的待接收批次，扫码查看详情并整批确认；确认前不纳入本班库存 |
| 已接收物料 | 新台账中已确认的来料批次与余量，可单批/多批出库、登记丢失；默认只看还有可用量的批次，可切换全部 |
| 出库记录 | 一次出库一个 CK 批次、一个条码，打开查看全部明细、确认状态和合计，单联汇总打印；单笔手工历史单也保留 |
| 丢失记录 | 来源批次、流水号、材质、丢失件数和重量、原因、登记人及时间；只追加，不覆盖原接收单据 |

件数和重量各自独立计算，重量为 kg、三位小数，不按比例自动推算。对每个来源批次：

- 当前库存 = 已接收量 − 已确认转出量 − 内部在途量 − 已登记丢失量。内部转料提交即离开本班库存；确认接收时在途转为确认转出，上序余额不再减少，下序库存增加。
- 内部在途 = 本班已提交且尚待下序接收的有效内部转料，不计入任何一端班组库存。全厂在库与内部在途之和为全厂持有物料，内部交接不重复增加总量。
- 可用量 = 当前库存 − 对外待确认占用量。库房对外出库及检验发货仍在本班确认后正式扣库，不受本次内部转料调整影响。
- 未接收单修改件数/重量时同步调整扣减与在途；作废将相应在途物料退回上序库存。确认后锁定，幂等重试不再次扣减或入库。
- 同一来源分批转给不同班组时，各笔保留明确关联和独立状态。

接口 `on_hand_quantity/weight` 为上述当前在库量，新增 `in_transit_quantity/weight` 为内部在途。`reserved_quantity/weight` 为兼容旧接口仍返回全部待确认转出（内部在途 + 对外预留）；它不是全部仍占本班库存，不能再用“当前库存 − reserved”计算可用。确认转出 `dispatched_quantity/weight` 字段含义保持不变。

内部转出的趋势、去向分析和机器人大屏“今日转出”按有效单据提交时间统计，作废单不计入；接收按确认时间统计，不因跨日接收重复计为当日转出。对外出库及检验发货仍按本班确认时间统计。库存排行、材质构成和库龄仅统计在库余量，不将内部在途叠加为库存。

### 批量出库

一次选择 1–100 个不同的已接收来料批次，只选择一个接收班组，逐行填写本次件数、重量。每行至少一项大于 0，两项均不得超过该来源的可用量。每行保留来源流水号、材质、单据字段和 TL 明细标识；整次提交生成 CK 批次号，Code 128 只打印这个 CK 码。扫码查询整批，下序一次确认所有待接收明细。不是把不同来源的库存合并为一条，也不改写历史单号。

整笔事务校验并提交，任意一行不满足余量、归属、状态或库房分类要求时，整笔不写入。来源批次按 ID 顺序加行锁，扣减读取采用 MySQL 当前读，避免同时出库/丢失导致超扣。相同幂等键、相同内容重试只返回原记录；改变内容须使用新键。

待接收出库单编辑数量/重量时，排除自身原占用后重新校验。流水号、材质、来源关联不能改；整组目标不能逐行变更，需作废相关待接收单后重新出库。确认后永久锁定。历史整组有已接收和待接收时显示“部分接收”，整批确认只处理剩余待接收明细，不重复确认已完成或作废项。

打印为单联 A4 汇总单：一个 CK 条码、各行流水号/材质/类型/件数/重量、合计、上下序与操作时间和签名位置。常规批次尽量一张 A4；明细很多或文本很长时完整续页，不缩成不可读小字、不截断或漏印物料。独立手工转料、库房入库和旧 TL 码保持兼容。

### 丢失登记

本班组长选择已接收批次，填写丢失件数/重量及必填原因。只能扣减尚未出库或占用的可用量；不允许修改原接收数量，也不将丢失记为转入“转废班组”。重复提交受幂等保护。接收前差异仍通知上序改单，不在待接收物料上登记丢失。

### 历史与范围

`20260906_0007` 为历史记录保留 `stock_tracked=false`，不推断缺少来源关联的库存，不补造历史丢失。新确认接收设为 true，之后从该来源进行出库和丢失登记。页面提示未纳入台账的历史已接收批次数，历史单据仍在全局转料记录和流水追踪中查询。

手工新建转料用于首次交接或尚无台账来源的记录，不会自动扣减任一同流水号历史库存；已在台账内的料必须通过“已接收物料 → 出库”。本轮未建设期初盘点导入或历史批次人工关联工具。

检验发货与库房接收是两种结束路径，不要求检验发货后再强制过库房。库房对外出库与检验发货按第 11 节独立记录并由本班组确认；不涉及公司主系统同步或财务结算。

### 新接口与发布

所有新接口前缀为 `/api/team-materials/{team_id}`，登录后可查询；写入限定有效 TEAM 账号且绑定相同 team_id。

- GET `/overview`：材质纵览、汇总、待接收统计及历史未纳入数。
- GET `/stock`：分页来料及余额，参数 query、material_type、availability=available/all、page、page_size。
- GET/POST `/losses`：分页丢失记录 / 幂等登记；查询支持来源批次 ID。
- GET/POST `/dispatches`：服务器分组分页 / 幂等批量出库；查询支持关键词、接收班组和 pending/partial/received/voided 状态。

转料响应追加 stock_tracked、source_transfer_id、source_transfer_batch_no、dispatch_no；批次详情追加 loss_records，列表为空数组。新增 `material_dispatches` 和 `material_losses`，外键限制删除引用来源，增加按班组时间、来源状态及出库组关联的六项索引。包含搜索仍不承诺 B-tree 范围定位。

台账初版对应 `20260906_0007`，手工入库对应 `20260906_0008`；最新版需先备份并迁移至 `20260907_0010`，再执行 `python -m app.configure_material_teams` 配置八个正式编码。配置脚本只补缺少的正式班组和明确的“扎板 → 轧制”目录更名，重复执行不重复创建，名称/编码/分类冲突会整笔退出。不会删除旧组、停用账号或改绑班组。上线需另行部署，此文不代表线上已更新。

## 10. 库房手工入库（2026-09-07 补充）

库房暂不依赖公司主系统的入库/出库接口。有效库房班组长可在库房工作台“手工入库”，手工填写流水号、材质、物料类型、件数、重量和必填入库说明；其余物料单据字段仍可补充。入库说明记录实际来源或用途，例如外部来料、实物清点后的期初建账；不虚构 ERP 单据或同步成功状态。

- 仅账号绑定正式库房 `FACTORY-WAREHOUSE` 且 kind=warehouse 可提交；管理员和其他班组不能代入库。
- 不选择转出或接收班组，库存归属自动取登录库房。来源班组为空，明确标注“库房手工入库”，不是“库房 → 库房”。
- 数量、重量至少一项大于 0；件数非负整数，重量 kg 最多三位小数，沿用八类物料分类。
- 提交即入账，生成独立 TL 批次及 Code 128，状态为 received、stock_tracked=true，并记录 stocked 审计；入库人与接收入账人为同一操作者。
- 入账后原单锁定，不需要再点接收，不支持直接修改或作废。提交前核对；网络结果未知时用原幂等键与原内容重试，不能重新开一笔代替查询。
- 入库批次进入库房纵览及已接收物料，可作为单批/批量出库、丢失登记的来源；后续转料有正常的库房转出方和目标班组，不继承“手工入库”类型。
- 库房新增“入库记录”页签，筛选手工入库根记录。其他班组转回库房仍走待接收确认，确认后入库存但不列为手工入库，不能重复登记。
- 全局记录、条码详情、打印、流水追踪可识别入库起点和后续交接；不把手工入库当成在途或再确认一次。

接口为 GET/POST `/api/team-materials/{team_id}/receipts`。POST 必填上述字段和 idempotency_key，禁止传 source_team_id、next_team_id、status、entry_kind 等系统字段。GET 支持 query、material_type、page、page_size，返回与转料列表一致的分页格式。

转料响应新增 entry_kind（transfer / warehouse_receipt）；仅手工入库的 source_team_id、source_team 为 null，其 next_team 为库房。普通班组转料仍强制具备真实转出方。`20260906_0008` 新增类型字段、来源一致性约束和库房入库时间索引；旧记录全部保留 transfer，不自动产生或补算库存。入库与审计、编号分配在同一事务中，幂等重试不能重复增加库存。

目前提供逐笔手工建账，不提供批量期初导入、历史来源自动关联或库存调整冲销工具；不直接覆盖历史余额。公司主系统对接仍属后续范围。

## 11. 库房对外出库与检验发货（2026-09-07 追加）

| 模式 | 发起班组 | 确认班组 | 确认后的库存位置 |
| --- | --- | --- | --- |
| 内部转料 | 有库存的本班组 | 指定接收班组 | 接收班组 |
| 对外出库 | 正式库房 | 库房本班组 | 离开内部台账，不新增内部库存 |
| 发货 | 正式检验 | 检验本班组 | 离开内部台账，不强制经过库房 |

- 从本班组“已接收物料”选取 1–100 个来源批次；单次 CK 提交的模式及去向一致，每条 TL 保留来源、流水号、材质及自己的件数/重量。
- 对外模式必填去向（客户、收货单位或外部位置，最多 240 字），可填写出库/发货说明。不得同时选择内部接收班组，不建立虚拟下序或“自己转给自己”的内部转料。
- 创建后为待出库确认/待发货确认，先占用来源可用量。本班组核实整批明细后一次确认全部待确认项，其他班组、管理员均不可代确认。
- 确认后记录实际确认人、时间及审计，状态 `dispatched`，显示为已出库或已发货。原单永久锁定，不再修改或作废，也不会进入任何班组“待接收”。
- 未确认前可修改允许的单据字段、件数/重量和说明，修改重新检查可用量；来源流水号、材质及分组去向不可改。改去向需先作废相关未确认批次再重建。作废释放占用。
- 件数和重量独立计算，当前库存口径以第 9 节及 2026-09-12 修正为准：当前库存 = 已入账量 − 内部已接收转出量 − 内部在途量 − 对外已确认出库量 − 丢失量；可用量仅再减对外待确认占用。对外确认把预留变为已出库，不重复扣可用量；不能再次从当前库存扣减内部在途。
- 扫码使用整批 CK Code 128 条码，旧 TL 码仍兼容；出库记录、单据详情、打印和同流水号追踪保留真实外部去向与发运状态，不展示“已被内部班组接收”。这是物料离开小循环的记录，不代表 ERP 同步、客户签收或财务结算。

接口扩展：

- POST `/api/team-materials/{team_id}/dispatches` 增加 `entry_kind`，默认 `transfer`，其余为 `warehouse_outbound`、`inspection_shipment`；外部必填 `external_destination`，`next_team_id` 必须缺省或 null。
- GET 同一路径支持 `entry_kind`、`status=dispatched`；关键词可搜索外部去向。外部分组部分完成返回 `partial`，所有非作废行完成返回 `dispatched`。
- 兼容保留 POST `/api/material-transfers/{batch_no}/confirm-outbound`，新批量页面统一使用下述 CK 整批接口；独立 TL 的 `/confirm` 仍只负责内部接收。
- 响应外部记录的 `next_team_id/next_team` 为 null，新增 `external_destination`、`dispatched_by/dispatched_by_user_id/dispatched_at`；`stock_tracked=false`，待确认允许 `confirm_outbound`，审计动作为 `dispatched`。
- `20260907_0009` 保留旧行不推断业务类型，扩展去向约束、出库确认字段与幂等键、按来源班组/类型/时间索引。确认和审计同一事务；并发重试使用当前读，保证返回最新确认状态和完整审计。

## 12. 整批扫码与确认接口（2026-09-07）

- GET `/api/material-dispatches/{dispatch_no}`：按唯一 CK 号读取完整明细与历史，不受列表分页影响。
- POST 同路径 `/confirm`：仅内部目标班组整批接收；`/confirm-outbound`：仅库房或检验本班组确认外部出库。
- 请求必填 `idempotency_key`、`expected_revision`（GET 返回的 64 位内容版本摘要）。来源、明细行、批次头按固定顺序锁定，确认人与每行状态、审计同一事务提交；出错不留半批。
- 摘要包含明细 ID、版本、状态。核对后任一明细修改、作废或由旧接口确认，返回 409，须刷新后重新核对。相同确认键及原摘要重试返回已完成结果；同键用于别批或改请求不允许。
- 响应新增 `barcode_payload=dispatch_no`、`barcode_type=CODE128`、`source_team`、`revision`、`pending_line_count`、`allowed_actions`、`locked` 和 `confirmed_by/confirmed_by_user_id/confirmed_at`。作废项保留展示但不计入合计。
- 迁移 `20260907_0010` 只为已有出库批次头添加可空确认字段、确认键唯一约束和确认人外键。原 CK、TL、来源、状态、审计原样保留；历史确认信息不补造。查询沿用 CK 唯一索引和明细 `dispatch_id` 索引。
